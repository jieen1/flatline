# ADR-23: Codex 轮级 token 的差值归属

- 状态：accepted
- 日期：2026-08-25
- 决策者：主 agent 提案（用户方向指令的延续）

## 背景

ADR-22 只覆盖了 Claude Code 的逐消息 usage。本机 30 天 203 次中断里 Codex 占绝大多数，
全部不可测——"中断的价签"只对 13% 的中断成立。

Codex 的 `event_msg/token_count` 记录携带 `total_token_usage.total_tokens`——**会话运行总量**，
且在轮内流式更新（本机实测：活跃轮内每 3–10 秒一条，总量单调递增）。它不按消息记录，
因此逐消息口径不适用。

## 决策

**运行总量差值、按用户轮锚定，在解析器内计算，零新增事件：**

1. 解析器顺序走转写：`lastTotal` 随每条 token_count 推进；一条**真实用户消息**（注入块与
   `<turn_aborted>` 副本已被注入过滤排除）打开一个轮，基线 = 当时的运行总量；
   **下一条用户消息、`turn_aborted`、或文件结束**关闭该轮，轮成本 = 关闭时运行总量 − 基线，
   写到**打开该轮的用户消息**的 payload（`turn_tokens`）上。
2. 前提守卫：整个会话一条 token_count 都没有（老版本 Codex），则不产生任何轮成本——
   缺失保持缺失，不写零。
3. 中断轮的成本**只低估、不高估**：中断时在途请求的 token 不在任何 token_count 里，
   运行总量从未包含它。判定规则一句话：*"Codex 轮成本 = 该轮结束时运行总量 − 开始时运行总量
   （harness 自己的累计值的差值归属）；中断时在途的部分未被任何记录包含，因此只低估。"*
4. `history.ParserVersion` 推到 `parser/8`：全量重读，payload 经 ADR-22 的刷新通道原地更新。
5. `/api/v1/insights` 中断块按来源取数：claude_code 走逐消息求和（ADR-22），
   codex 读中断前最后一条用户消息的 `turn_tokens`。两类的可测数合并进 `turn_measured`。

## 为什么差值是计算而不是推断

总量是 harness 自己写下的累计值；轮成本是两个累计值的减法，与 `active_ms`（时间戳差值）同类。
它不猜测"哪个消息花了多少"，只回答"这一轮期间 harness 计入了多少"。
不采用 `last_token_usage`（它是流式段级数据，语义随 Codex 版本漂移），
不按会话总量比例分摊（伪造精度）。

## 后果

- 正向：中断价签的覆盖从 13% 扩到 Codex 全部有 token_count 的中断；轮成本同时是后续
  "轮成本分布 / 卡死循环代价"的地基。
- 代价：全量重读一次；用户消息 payload +~30 字节。
- 边界：压缩（compact）后的会话总量若被 Codex 重置，差值为负——负差值不写（保持缺失），
  防止把重置伪造成"负成本"。
