# ADR-20: 代价与机会洞察层（insights 是既有事实的只读投影）

- 状态：accepted
- 日期：2026-08-25
- 决策者：用户（产品方向指令）+ 主 agent 提案

## 背景

系统当前回答"这段时间发生了什么"（总览）与"哪里反复卡住"（摩擦页），两者都停在**描述**：
计数、生命周期、机制解释都是事件层的，没有回答用户真正关心的问题——
**这些记录证明我在哪里付出了成本、哪里有可回收的浪费、哪里有可改进的流程**。

本机真实数据（2026-08-25，1173 个会话）验证了三类此前没有被任何页面摆到台面上的事实：

1. **中断的上下文**：330 次 `user_interrupt`，71% 集中在一个项目；中断前最后一次工具调用
   一半以上落在等待长进程的工具上（`exec_command` / `write_stdin`）。
   中断是用户用脚投的票，但没有任何页面把它聚合成"疼在哪"。
2. **零改动的高投入会话**：30 天内 21 个主会话 token ≥ 5M 且没有记录到任何编辑工具改动，
   合计约 7.0B token（约占同期 token 的一半）。调研会话合法零改动，
   但这个量级应当被看见、可下钻，而不是混在总量里。
3. **卡死循环**：同一摩擦签名在同一会话内连撞 5 次以上的记录真实存在
   （如 `apply_patch verification failed` 在一个会话里 52 次）——agent 在重复同一个失败动作。

约束（不可妥协）：

- 证据纪律（AGENTS.md §2）：不伪造、不归因、无健康分、缺失≠零、每条可下钻到分子分母；
- ADR-8：每条判定规则一句话可解释；
- 事件层只存会话级 usage 聚合，**逐消息 token 不在库里**——"中断的那轮烧了多少 token"不可计算，不做。

## 决策

新增一个只读端点 `GET /api/v1/insights`（`internal/api/insights.go`），把**既有 canonical 表里已经在库的事实**
按"代价与机会"重新投影成有限的几条洞察，每条自带：标题（中英）、事实句（中英）、
判定规则一句话（中英）、结构化 facts、下钻链接。总览页在 KPI 之后新增"代价与机会"区块渲染它。

边界：

1. **不新增表、不新增迁移、不写任何数据**——全部是读时 SQL 聚合（friction_records / session_usage /
   session_stats / session_commands / events / 既有 coverage 机制）。
2. **洞察的候选集是封闭的**（六类）：中断上下文、零改动高投入、卡死循环、重复读取、
   规则覆盖缺口、环境缺命令。不做开放式的"智能分析"，不引入 AI 层（MVP 边界）。
3. **每条洞察必须有判定规则原文**（`criterion` / `criterion_en`），排序键写进规则句子里
   （如"按受影响会话数排序"），不出现分数、权重、百分制。
4. **零改动高投入的口径必须如实**：改动行只统计编辑类工具（Edit/Write/apply_patch）记录的改动，
   bash 改写不计入；调研/分析会话本来就可能零改动——页面陈述事实与口径，判断留给读者。
5. **中断代价只陈述可计算的事实**（中断前的项目/工具/调用密度），不估算 token 损失
   （逐消息 usage 不在库里，估算即伪造）。
6. 阈值（token ≥ 5M、同会话连撞 ≥ 5 次、重复读取 ≥ 3 次等）是常量，写进判定规则句子，
   与总览既有区块共用同一口径（重复读取沿用总览 reread 阈值）。

## 后果

- 正向：用户第一次能从自己的记录里直接看到"疼在哪、浪费在哪、哪些机制没被规则覆盖"，
  每条都可下钻到会话/签名/文件；机制字典扩容（hint 规则）让覆盖缺口与机制分布同步变厚。
- 代价：`/api/v1/insights` 与 `/overview` 有少量重复扫描（friction set 装载两次），
  实测在可接受范围内即接受；端点走 `s.cached`，`data_version` 不变时零成本。
- 不解决：`coverage_gaps` 不分项目（已知契约毛边 §27.8）维持原状；中断轮次的 token 损失
  在事件层存下逐消息 usage 之前不可计算，留待数据层演进。
