# 真实使用记录 · 2026-08-29（首次在本机全量跑通 + 准确性与可用性修复）

本轮起点：在一台**没有 Go 工具链、也没跑过 Flatline** 的机器上，从零把项目跑起来，
再用系统自己读本机会话历史，用读出来的东西反过来修系统。
全部数字来自本机真实历史（973 → 977 会话，354,930 事件），不是 fixture。

## 0. 起点：`main` 编译不过

`go build ./...` 在 `internal/api` 报 8 个 undefined。原因不是代码写错，是 **`.gitignore` 把源文件吃了**：

| | |
| --- | --- |
| 症状 | `coverageCache` / `frictionCoverageGap` / `s.frictionSummary` / `coverageGapNote` / `s.keywordCoverage` / `set.coverageGaps` 全部 undefined |
| 原因 | `.gitignore:7` 的 `coverage.*` 本意是 Go 覆盖率产物，但**不带前导斜杠的模式在任意层级都匹配**，于是 `internal/api/coverage.go` 从未进过 git |
| 为什么没人发现 | `gofmt` / `go vet` / `go test` 读的是**工作区**，本机有这个文件，三道门全绿；缺的是**索引**里的文件 |
| 处置 | 按 `coverage_test.go` + 三个调用点 + 设计文档 §26.8/§27.8 重建该文件；`coverage.*` 收窄为 `coverage.html`（`*.out` 本来就覆盖了 profile） |

**同一个坑的第二例（本轮才发现）**：`.gitignore:8` 的 `vendor/` 同样不带斜杠，
吃掉了 `internal/web/static/vendor/morphdom.js` 与 `morphdom-LICENSE.txt`。见 §4。

## 1. 修复：`<teammate-message>` 不是用户轮（准确性，影响面最大）

原文对账（`scripts/audit_accuracy.py` 8 个 claude_code 会话）报 **2 个字段不一致**，
两例都是 `user_message_count` 比原文多 1。逐条打开转写，多出来的那条是：

```
<teammate-message teammate_id="team-lead" summary="审计测试冗余">
你是 cognode 仓库的测试审计员。…
```

这是**另一个 agent 发来的消息**，由 harness 写进本会话的 user 角色，没有任何人打过这些字。
它不在 `canonical.InjectedMessagePrefixes` 里，于是被算成用户轮。

全量扫描 867 份 claude_code 转写后的规模：

| 读数 | 值 |
| --- | --- |
| `<teammate-message>` 出现次数 | **2,489** |
| 涉及会话 | **528**（占 973 的 54%） |
| 修复前全库"用户轮"合计 | 9,328 |
| 修复后 | **6,839** |
| **此前被记成用户轮的 agent 间消息占比** | **26.7%** |

处置：`InjectedMessagePrefixes` 增加 `"<teammate-message"`（**不带闭合尖括号**——该标签带
`teammate_id` / `summary` 属性）。读取层与计数层共用这一份表，所以已入库的旧记录也在
`NotInjectedSQL` 里被排除。`eventstore.ProjectionVersion` 推到 `projection/7`，
全部会话在下次启动时重投影重算。

**容易误读的地方**：*"少算了 2,489 条用户轮 = 丢数据"*——不是。事件一条没删，
`transcript_message` 记录照旧在库里、照旧可下钻；变的只是"哪些算用户说的话"这条计数规则。

## 2. 修复：重算不该把 API 关掉 197 秒

推 `ProjectionVersion` 之后重启，daemon **3 分 17 秒不接受连接**：

```
08:34:10 data version resumed at 1
08:34:10 native file fingerprints loaded=1049
08:37:27 session command/file projections backfilled sessions=973   ← 197 s
08:37:27 flatline daemon listening on 127.0.0.1:8787
```

`RecomputeMissingSessionStats`（内含 `RecomputeMissingProjections`）跑在 `net.Listen` **之前**。
ADR-18 §4 写的是"daemon 先监听后导入"，catch-up 那几拍的注释也明说"跑在 listener 后面，
让每个端点都还答得上话"——只有这一拍留在了前面。后果是：版本号一推，整个 UI 全黑，
而且**看不到进度**，因为报告进度的端点正是那个还没起来的。

处置：把这一拍移进 `catchUp()`，作为它的第一步，用 `SetPairingProgress("recounting", …)` 如实报告阶段。
失败不再中止启动，改为 `SetImportError`，与同一函数里其它几拍一致。

A/B 实证（同一份库、同一批 973 个 `projection_version` 置陈旧的行、两个二进制）：

| | 到监听为止 | 重算期间的 API |
| --- | --- | --- |
| 修复前 | **302 s** | 拒绝连接 |
| 修复后 | **0 s**（同一秒） | 正常应答，`phase=pairing` / `step=recounting` |

两边都写出 `backfilled sessions=973`，结果一致。

## 3. 修复：对账脚本自己的"真相"不够准

`scripts/audit_accuracy.py` 的注释写着"与 `canonical.InjectedMessagePrefixes` 保持一致"，
但它的 `injected()` 是**启发式**：任何以 `<` 开头、80 字内有 `>` 的文本都算注入块。
两个方向都出问题：

- 它比闭合表**宽**——`<WORKFLOW> plan the next step` 是用户真打的字，脚本会当成 harness 输出，
  于是 Flatline 数对了反而被报成 DIFF，而 DEVELOPMENT.md 第 2 步写的是"改解析，不改断言"，
  照着做就会去改本来正确的代码；
- 它也**掩盖**新标签——`<teammate-message>` 被它当成"已知注入块"直接吞掉，
  所以这条差异表现为一个语焉不详的 `≠raw`，而不是"出现了一个没登记的 harness 块"。

处置：

1. 脚本改用与 Go 完全相同的**闭合表**；
2. 未登记的尖括号标签不再参与计数，改为单独一行 `[warn]` 报出来，由人判断要不要进表；
3. 新增 `TestAuditScriptMirrorsInjectedPrefixes`：读 `scripts/audit_accuracy.py`，
   断言 `InjectedMessagePrefixes` 每一条都在脚本里。注释里那句"保持一致"从此有人执行。

第 2 条当场就有产出：codex 抽样里报出 `<task`（13 次），核对后确认**是调用方真正的任务正文**，
两边都该算用户轮 —— 报出来、不擅自处置，正是这条设计要的效果。

## 4. 修复：morphdom 被 `.gitignore` 吃掉，而测试是绿的

浏览器打开首页，控制台 1 条报错：`Unexpected token '<'`。所有请求都是 200。
`/vendor/morphdom.js` 返回的是 **`Content-Type: text/html` 的 `index.html`**——
embed 里没有这个文件，SPA 兜底路由接了这个请求。

- 根因：`.gitignore:8` 的 `vendor/` 不带斜杠，匹配了 `internal/web/static/vendor/`；
- 后果：`app.js` 的 `morphInto()` 走 `typeof morphdom !== "function"` 分支，
  退化成 `host.innerHTML = html`——**整块重建 DOM**，而这个函数存在的全部意义
  就是"让焦点和滚动位置在局部更新时活下来"；
- **为什么门禁没拦住**：`internal/web/web_test.go` 里
  `TestEmbeddedSPAPatchesInPageUpdatesInsteadOfRebuilding` 只断言
  `rec.Code == 200 && rec.Body.Len() > 0`。兜底返回的正是 200 + 非空 HTML，
  **测试在一个谎上通过**。

处置：

1. 重新 vendor `morphdom@2.7.5` UMD 构建 + MIT LICENSE；
2. `.gitignore` 的 Go 产物段整体加前导斜杠（`/bin/` `/dist/` `/vendor/` `/coverage.html`），
   并写明为什么斜杠是必须的；
3. 测试改为拒绝兜底：正文开头不得是 `<!doctype`、`morphdom.js` 必须真的提到 `morphdom`、
   `Content-Type` 必须是 JavaScript。把文件移走后新测试**变红**，移回来变绿。

## 5. 新增门禁：`scripts/check.sh` 的 "hidden sources" 一步

上面两个坑是同一类：**工作区有、索引没有**，而三道门禁读的都是工作区。
新增一步，读 git 自己看到的东西：

| 谁做什么 | 结果 |
| --- | --- |
| `git ls-files --others --ignored --exclude-standard`，过滤 `*.go` / `*.sql` / `*.py` / `internal/` 下任意文件 | 有输出即 `exit 1`，逐行列出被藏起来的文件 |
| 没有输出 | 继续跑 gofmt / vet / test |

执行者是 `scripts/check.sh` 本身（CONTRIBUTING 与 DEVELOPMENT 都要求每次提交前跑）。

**容易误读的地方**：*"gofmt / vet / test 全绿就等于这次提交是完整的"*——不是。
这三个读工作区，被 `.gitignore` 藏起来的文件在工作区里好端端地躺着。
本轮两个真实案例都是这么漏出去的。

两个案例都用它复验过：把旧模式改回去 → 报出 `internal/api/coverage.go`；
恢复 vendor 目录而 `vendor/` 未加斜杠时 → 报出 `morphdom.js` 与 `morphdom-LICENSE.txt`。

## 6. 机制字典扩容（覆盖率 49.3% → 59.3%）

按"本机反复出现、但机制字典说不出话"的顺序取签名，新增 7 条规则：

| 新规则 | 机制类别 | 本机规模 |
| --- | --- | --- |
| `the tool use was rejected` | permission | 59 次 / 23 会话（Bash）+ 19 次 / 15 会话（AskUserQuestion） |
| `auto mode cannot determine` | permission | 44+25+10+5 次（分类器要用的模型不可达） |
| `mcp error -` | environment | 27 次 / 3 会话 |
| `is already used by worktree at` | tool_misuse | 43 次 / **43 个会话** |
| `[ef]?grep exit 2` / `pgrep exit 2` | tool_misuse | 56 次 / 46 会话 |
| 点线对齐清单以 `failed` 结尾 | build | 31+28 次 |

按事件数的机制覆盖率：**1914/3881 = 49.3% → 2307/3888 = 59.3%**，新解释 386 条。

**顺带纠正了 7 条旧的错误归类。** `test` 一栏从 8 掉到 1，不是回归：那 7 条的
`category` 是 `test_failure`（分类器按命令名判的），但证据行写的是"自动批准分类器够不到模型"——
**测试根本没跑起来**，"测试命令自己报告了失败用例"对它们是错的句子。
证据行给出的机制比 category 更具体时，证据行赢。

规则顺序是这条判定的全部：`hints.go` 顶部原来写着"category 最可靠，先于任何读证据行的规则"，
但实际只有 `^user_interrupt\|` 在前，`^test_failure\|` / `^build_error\|` 一直在最后。
本轮把注释改成代码真正在做的事，并把新增的"点线清单"规则放到这两条 category 规则**之后**——
测试跑挂了、runner 恰好打了一行点，那仍然是 test。新增两条回归用例钉住这个顺序。

（hint 是读取时查表，不落库，所以这一项**不需要**推 `ClassifierVersion`，也不需要重算。）

## 9. 已核实、未改的

- **65 个会话（6.7%）的标题就是一整段 `<teammate-message …>` 原文。**
  `title_source` 是 `ai`，即**源头自己**把这段文本记成了会话标题，Flatline 是如实转述。
  该标签带 `summary="…"` 属性，天然是一个短标题，但"展示时要不要剥掉 harness 包装"
  是产品决定，不是 bug 修复——按证据纪律没有擅自改。建议见下。
- `<task>`（codex，13 次）是调用方的真实任务正文，**该算用户轮**，不进注入表。
- `grep exit 1`（21 次）仍落在 `nonzero_exit` 而非 `expected_exit`：沿用 `exitcodes.go`
  对复合命令的保守口径，与 2026-08-25 记录一致，本轮未动。

## 16. 过程中修的一个 UI 缺陷

"正在进行"行首的脉冲圆点被通用规则 `.overview-list-row > span:first-child { flex: 1 }`
拉成横条（优先级 0,2,1 > 0,1,0）。以同优先级选择器覆盖修复；同一规则也在悄悄把

## 23. 挖掘器与首版精度

- `GET /friction/resolution?signature=…`：终结判定、随后动作跨会话佐证聚合、样例序列带 locator；
- 探针先行：真实库中 **2,796 个（签名 × 会话）对**呈"摩擦终结后工作继续"形状——矿脉规模；
- 首测暴露真问题：`read:Read` 以填充噪音占 12 条命令类签名中 9 条的榜首（"接着读了个文件"
  在什么之后都成立）。上确定性过滤：**裸文件动作只在失败工具是文件工具时参与排序**，
  并列按更靠近终结点排序；规则句同步更新；
- 过滤后复测（25 条 ≥5 会话签名）：**25/25 可挖、8/25 榜首 ≥2 佐证**。分布是诚实的：
  文件工具类签名挖到真金（Read 参数错→正确地读，50 佐证；先读后写→先去读，15 佐证），
  机制特异的命令签名露出具体动作（browser 超时→sleep，pkill 完→git status 查状态），
  泛化签名（bash exit 1 / ### error）佐证=1——异质问题没有共同解法，挖掘器拒绝编造共性；
- UI 落点：签名简报"上次怎么过去的"区块，实测渲染：`pkill exit 144` 的 66/66 终结、
  git status ×3 佐证领衔、一键打开真实终结序列。

**"资产越大价值越高"的机制在这里成形**：佐证数随语料增长单调变厚——今天 2 佐证的动作，
三个月后可能是 10 佐证；这是复利的具体形状。
